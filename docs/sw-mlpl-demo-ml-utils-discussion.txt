GGUF is almost ideal as the first serious target
GGUF is structured in a way that makes bounded-memory inspection practical. Its file structure consists of a header, metadata key/value pairs, tensor descriptors containing dimensions/type/offset, and then an aligned tensor-data blob.

That means an inspector can initially read only:

header
metadata
tensor directory
and produce a surprisingly rich visualization without decoding the weight blob at all.

Then:

inspect tensor
      ↓
seek to tensor offset
      ↓
read N blocks
      ↓
decode or sample
      ↓
calculate statistics
      ↓
discard source bytes
So one of your first demonstrations could handle a 100+ GB GGUF file while maintaining a tiny fixed memory footprint.

That is a compelling general-purpose-language demonstration in its own right.

Safetensors should actually come first
Implementation-wise, I'd do Safetensors before GGUF.

Safetensors deliberately has a simple representation and supports accessing individual tensors and slices without loading the entire model; Hugging Face describes it as safe and zero-copy and documents partial tensor access.

So I would sequence the format work:

Safetensors metadata inspector.

Safetensors tensor streaming/statistics.

Safetensors 3D visualization.

GGUF metadata/tensor-directory inspector.

GGUF unquantized tensor decoding.

GGUF simple quant formats.

GGUF K-quants and other block formats.

Conversion/quantization.

That gives you useful demonstrations much sooner.

"Unsafe weights" could become a security demo
I'd explicitly call that category something like PyTorch/pickle checkpoint inspection, because the distinction is educational.

Current PyTorch documentation warns that torch.load() uses an unpickler and says not to load untrusted data; it supports a restricted weights_only mode and memory-mapped storage access.

I therefore would not make:

load_weights("random-internet-file.pt")
implicitly execute Python serialization machinery.

Instead:

info = inspect_checkpoint("foo.pt")
could perform passive structural inspection.

And perhaps:

safe = external("pytorch.weights_only", "foo.pt")
would explicitly invoke a hardened external converter.

That's a nice teaching comparison:

pickle/PT       executable serialization
safetensors     declarative tensors
GGUF            inference-oriented tensors + metadata + quantization
The biggest thing this will force into the language
Surprisingly, I don't think it is graphics.

It is real binary data types.

From the current README, the CPU reference representation is built around DenseArray and the architecture describes host arrays as bit-exact f64 reference arrays.

GGUF manipulation makes pretending everything is an f64 increasingly awkward.

You will want at minimum something conceptually like:

u8
i8
u16
i16
u32
i32
u64
i64
f16
bf16
f32
f64
plus typed arrays:

bytes : u8[4096]

magic   = read_u32_le(bytes, 0)
version = read_u32_le(bytes, 4)
And ultimately:

x = reinterpret(bytes, f32)
without numerically converting every byte.

That then forces useful general-language operators
One fairly compact core addition would unlock a lot:

typed integer/byte arrays;

and, or, xor, shifts and masks;

little-/big-endian encode/decode;

cheap array views/slices;

streaming/chunk iteration;

binary read/write/seek;

binary packing/unpacking;

bounded reductions over streams;

explicit reinterpretation versus conversion.

These aren't "GGUF features."

They make sw-MLPL substantially more complete as a systems/data-processing language.

Streaming is probably the second major language forcing function
I would resist special functions like:

analyze_gguf(...)
in the core.

Instead you want to make this elegant MLPL:

file_chunks(path, 1_MiB)
|> map(decode)
|> map(statistics)
|> reduce(merge_statistics)
or whatever the eventual sw-MLPL idiom is.

Conceptually:

source
  |> chunk
  |> transform
  |> filter
  |> scan
  |> reduce
That ties beautifully into demo-functional-pipelines.

The important property is:

memory complexity = O(chunk size)
not
memory complexity = O(file size)
This is exactly the sort of test that prevents array languages from silently assuming "the whole array is in RAM."

I'd distinguish streams from arrays
Don't make lazy arrays secretly mean streams.

They have different semantics.

Array
    finite
    known shape
    random access
    potentially reusable

Stream
    incremental
    possibly unknown length
    sequential
    generally consumed
Then things such as:

reduce(stats_merge,
       map(analyze_chunk,
           chunks(file, 1048576)))
have clear semantics.

A stream can ultimately produce an array:

collect(take(1000, stream))
but doesn't masquerade as one.

This will probably also improve dataset handling and training pipelines later.

On “unsafe” Python/PyTorch formats
Yes—your correction is important.

The danger is not inherent in the weights. The issue is formats based on Python serialization such as pickle, where deserializing an untrusted object can cause Python code or other callable behavior to execute.

Since sw-MLPL has no Python runtime and would not interpret pickle opcodes by invoking Python objects, merely analyzing bytes from such a file does not give it the same execution pathway.

That creates a rather interesting opportunity.

Instead of:

unsafe Python checkpoint
        |
        v
    Python loader
        |
        +---- potentially executes serialized behavior
you could deliberately build:

Python/PyTorch checkpoint
        |
        v
 sw-MLPL binary parser
        |
        v
 extract tensors only
        |
        v
 safetensors / GGUF
That would be an excellent demo.
In fact, I'd make it one of the headline applications of demo-ml-utils.

The goal would be something like:

Extract model weights from a Python-oriented checkpoint without executing the serialized program representation.

That is considerably more interesting than merely calling an external conversion script.

But there is an important distinction
“No Python runtime” does not automatically mean arbitrary pickle files can be safely converted.

A pickle stream is effectively a small stack-machine program. To recover objects from it, you still have to interpret its opcodes. Some opcodes refer to globals/classes/functions and are intended to cause construction or invocation behavior.

So the sw-MLPL implementation should treat pickle more like an untrusted executable file format than an ordinary serializer.

Conceptually:

                  pickle stream
                       |
                       v
                opcode parser
                       |
            +----------+----------+
            |                     |
            v                     v
      permitted subset       prohibited opcode/
                             object construction
            |                     |
            v                     X
      tensor metadata          reject
      tensor references
            |
            v
      raw tensor storage
You would parse, not “execute,” it.

That distinction itself would make a good educational demo.
